# 城市热门地点每周人工复核 V0.2

## 目标与边界

V0.2 给每个已开放城市增加周期性人工内容复核。一次“刷新”表示管理员完成了复核，不表示每周必须修改地点；如果联网检索没有发现实质变化，可以主动确认“本周无实质变化”并完成任务。

系统不运行 Cron、不自动联网、不调用 DeepSeek，也不抓取外部来源页面。外部 AI 只负责提出带来源的候选，任何结果都不能自动发布、下架、改名或调整 S/A/B/C。

## 完整操作流程

1. 仪表盘“城市数据复核”查看待复核、逾期、从未复核、正在复核和本周已完成数量。
2. 在城市管理查看上次复核时间、到期状态和当前任务，点击“开始本周复核”。
3. 系统根据 D1 当前已发布地点实时生成提示词，管理员复制给具备联网能力的 ChatGPT、Claude 或其他 AI。
4. 将 AI 返回的纯 JSON 粘贴到后台。Markdown 代码块、额外说明和非法 JSON 会被拒绝。
5. 点击“校验并预览”。此时只做 Zod 校验、城市匹配、数量限制、名称匹配、去重和字段级差异计算，不写候选表。
6. 确认预览哈希后才导入候选。原始 JSON 与预览哈希绑定，内容变化后必须重新预览。
7. 逐项查看当前内容、AI 建议、字段差异、来源、高德验证和确定性系统判断，选择接受、拒绝或忽略。
8. 所有候选不再待处理后，点击“完成本次复核”。只有这一步更新城市的 `last_content_review_at`。

后台路径：

- `/#/admin`
- `/#/admin/cities/:adcode/refresh`
- `/#/admin/refresh-runs/:runId`

## 到期计算

城市保存 `review_interval_days`、`last_content_review_at` 和 `last_refresh_run_id`，不保存冗余的下次到期时间。

- 默认周期 7 天，可改为 7、14 或 30 天。
- UTC 时间达到 `last_content_review_at + review_interval_days` 时到期。
- 到期当天显示“今天到期”；再经过完整一天后显示“已逾期1天”。
- 已开放但从未完成复核的城市显示“从未复核”。
- 草稿和停用城市不进入提醒。
- 高德 `verified_at`、生成提示词、预览、导入或只处理部分候选都不会刷新城市复核时间。

## AI 检索提示词

提示词由服务端根据实时城市和已发布地点生成，包含：

- 城市名称、adcode、本次日期和上次复核日期。
- 当前已发布地点的稳定 ID、名称、分类和级别。
- 8 个固定分类与 S/A/B/C 定义。
- 必须联网、提供 HTTPS 来源、只输出 JSON、没有变化时如实声明的要求。
- 禁止编造客流、票价、排队和营业状态。
- 新地点至少两个不同来源，关闭/改名/迁址优先官方来源。
- 没有联网能力时返回错误 JSON，禁止凭记忆生成。

上海提示词的关键部分示例：

```text
城市：上海
adcode：310000
本次检索日期：2026-07-26T00:00:00.000Z
上次复核日期：从未复核

当前系统已发布地点（稳定 spotId｜名称｜分类｜级别）：
- shanghai-the-bund｜外滩｜classic_landmark｜S

请务必联网搜索，优先使用官方网站、政府、权威机构和主流媒体……
只输出合法 JSON 对象，不要 Markdown、代码围栏或额外说明。
```

完整提示词会随 D1 当前已发布地点变化，不在前端写死。

## JSON 返回格式

最小“本周无变化”示例：

```json
{
  "schemaVersion": "1.0",
  "city": {
    "name": "上海",
    "adcode": "310000"
  },
  "researchedAt": "2026-07-26T00:00:00.000Z",
  "searchSummary": "检查官方网站、政府公告和权威媒体后未发现实质变化。",
  "noMaterialChange": true,
  "sources": [
    {
      "title": "上海市文化和旅游局相关页面",
      "url": "https://example.com/shanghai",
      "sourceName": "上海市文化和旅游局",
      "sourceKind": "government"
    }
  ],
  "existingSpotChanges": [],
  "newCandidates": [],
  "possibleClosedOrRenamed": []
}
```

新增地点、现有地点更新和疑似关闭/改名的完整字段结构由后台页面示例及系统生成提示词共同约束。`schemaVersion` 当前只接受 `1.0`；来源链接只接受 HTTPS；一次最多 50 条候选。

## 系统判断规则

系统判断完全确定性，不调用 LLM：

- 新地点来源少于两个不同域名：`needs_more_evidence`。
- 来源满足但未高德验证：`needs_amap_verification`。
- 高德验证成功、来源满足且未命中现有地点：`recommended_update`。
- 规范化名称高度相似或高德 POI ID 已存在：`possible_duplicate`。
- 关闭、迁址、改名：`high_risk_manual_review`。
- 只有空格、标点或等价内容变化：`no_material_change`。
- 结构、城市或匹配错误：禁止确认导入。

来源数量只是完整度提示。V0.2 不抓取来源页面，因此系统不会声称已经验证来源真实性。

## 高德与人工审核职责

高德只确认地点是否存在，并返回真实 POI ID、名称、地址、坐标及安全图片候选；高德不能决定地点是否值得推荐，也不能调整分类和等级。

管理员负责：

- 判断来源是否可信、变化是否真实。
- 决定是否接受分类、级别、文案和属性调整。
- 对关闭、迁址和改名进行最终高风险确认。
- 明确确认是否把变更应用到当前已发布地点。
- 处理所有候选并完成本次复核。

接受新地点只创建 `draft`，即使已通过高德验证也仍需走 V0.1 发布门槛。疑似关闭被接受时只记录人工决定，不自动下架。

## D1 migration

V0.2 新增：

```text
server/migrations/0002_weekly_city_refresh.sql
```

它给 `cities` 增加复核周期和时间字段，并创建 `city_refresh_runs`、`city_refresh_candidates`、单城市唯一活跃任务约束及候选索引。

本地：

```bash
npm run db:migrate:local -w server
```

生产：

```bash
npm run db:migrate:remote -w server
```

当前仓库还保留 `0002_admin_login_attempts.sql`，用于给已经应用过早期 V0.1 migration 的数据库补齐登录限流表。Wrangler 会按迁移文件名记录并分别应用。

## 无变化与高风险情况

“本周无变化”必须由外部结果明确返回 `noMaterialChange: true`，导入后还要由管理员点击“主动确认无实质变化”。只粘贴或导入不能完成复核。

关闭、改名和迁址始终视为高风险：

- 不自动下架。
- 不自动改名。
- 不清空高德 POI ID。
- 显示来源和高德结果。
- 必须逐项确认并记录审计。

## 为什么不做自动联网和 Cron

V0.2 优先建立可追溯的人工复核闭环。自动搜索会引入来源真实性、提示词漂移、费用、限流和错误自动扩散风险；Cron 只能发现到期，不能替代内容判断。当前阶段把“候选收集”和“线上修改”明确隔离更可靠。

后续可以升级：

- Cloudflare Cron Trigger 只生成到期提醒，不自动修改数据。
- 邮件或企业消息发送待复核数量。
- 受限的搜索服务自动收集候选，但仍进入同一预览、去重和人工审核流程。
- 为来源增加抓取时间、内容摘要哈希和失效检测。
- 增加多管理员复核与高风险双人确认，但不改变“候选不能自动发布”的原则。
