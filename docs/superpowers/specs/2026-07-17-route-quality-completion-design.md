# 路线质量整改闭环设计

日期：2026-07-17

## 目标

在不改变页面整体布局、产品流程、API 成功响应结构和现有 fallback 能力的前提下，补齐以下尚未闭环的问题：

1. 父级景点、父子 POI 和同父级子 POI 的聚合与去重。
2. 多路线候选的全局分配、有限重复和候选不足解释。
3. 候选充足时的时间利用率，以及不合理停留时间压缩。
4. 混合偏好、refine、replace-stop 路径中的自定义关键词约束。
5. 三个真实场景的全链路自动化与线上验收。
6. 取消后不写历史记录等缺失的验收测试。

## 非目标

- 不接入新的地图路线规划 API。
- 不重新设计页面，不新增产品入口。
- 不把 planner 模块重新合并成单体文件。
- 不依赖额外一次 LLM 调用完成标题、去重、时间或交通规则。
- 不根据缺乏依据的数据声称地点当前开放、可骑行或无需乘船。

## 总体方案

采用“内部元数据保留 + 两阶段候选装配 + 输出净化”的统一管线。

现有 food、scenic、wander、LLM 验证和 fallback planner 继续负责产生候选路线。统一策略层先完成 POI 质量与相关性判定，再根据路线目标、时间容量和全局占用情况分配地点。`parentPoiId`、`typecode`、偏好归属和质量分数只在服务端内部流转，返回 API 前全部剥离，因此客户端看到的成功响应结构保持不变。

## 内部数据模型

新增仅供 planner 使用的 `PlannerStop`，继承现有 `Stop` 并增加可选字段：

- `parentPoiId`：高德父级 POI ID。
- `typecode`：高德类型编码，用于判断美食、景点、文化和闲逛归属。
- `preferenceScope`：`food | scenic | wander`，用于混合偏好下选择对应的自定义关键词。
- `qualityScore`：相关性、可游览价值和来源排序形成的内部评分。

所有高德解析、地点验证、gap fill、refine 搜索和 replace-stop 搜索都要保留这些字段。统一输出函数负责移除内部字段。

## POI 身份与父级聚合

身份判断按以下顺序执行，不能在 ID 不同后提前返回：

1. 两个 POI 的 `amapPoiId` 相同：相同地点。
2. 一个 POI 的 ID 等于另一个的 `parentPoiId`：父子地点，视为同组。
3. 两个非空 `parentPoiId` 相同：同父级子地点，视为同组。
4. 缺少可靠 ID 时，使用标准化名称和 120 米内坐标判断。

分配时优先保留父级 POI；如果只有子 POI，则在同父级候选中保留质量最高、名称最像可游览地点的一项。不得为了达到数量下限重新加入硬过滤地点或低价值内部构件。

## 全局候选分配

统一策略改为两阶段：

1. **候选准备**：逐路线完成硬过滤、软降权、自定义关键词相关性、距离约束和父级聚合，形成带原始顺序及评分的候选池。
2. **全局分配**：按路线顺序分配。每条路线优先取得自己候选池中未被使用的高分地点；不足时从同类共享候选池补充；仍不足才允许有限重复。

重复时必须满足：

- 不在同一路线内重复。
- 后续路线最多补到其合理容量，不用重复地点强行达到推荐下限。
- 设置 `fallbackReason`，说明附近同类候选不足。
- 保留路线的方向与主题，不把明显不属于该路线类型的地点补入。

原有 `allocateDistinctPois` 将成为生产装配的一部分，不再只供测试使用。

## 时间预算与利用率

继续使用以下容量：

- 60 分钟：2–3 个。
- 120 分钟：3–4 个。
- 240 分钟：4–5 个。
- 480 分钟：5–7 个。

规则如下：

1. 上限和总预计时间是硬约束。
2. 总时间包含停留、起点到首站、相邻站移动和 5% 缓冲。
3. 推荐下限只在存在足够的同类、高质量、未使用候选时尝试满足。
4. 候选不足时允许低于下限，并返回候选不足原因。
5. 不把博物馆、正餐或景点压缩到低于各类型最低合理停留时间。单个地点仍无法放入预算时，删除该地点或返回无可行路线。
6. 删除地点时优先删除低相关、软降权、移动代价高的候选。

## 自定义关键词

关键词按偏好类别分别保存和应用：

- `customCuisine` 只约束美食候选。
- `customScenic` 只约束景点候选。
- `customWander` 只约束闲逛候选。

单一偏好和混合偏好都执行基础相关性保护。已知词使用同义词表，未知词按原词匹配。零相关候选不得进入对应类别的最终路线；弱相关候选可以保留在候选池末尾，但不能成为首选。

refine 和 replace-stop 请求继续携带原始自定义条件。refine Prompt 中未知距离写为“未知”，不得转换为 `0`。replace-stop 优先使用原地点类别与原始自定义词联合搜索，并在返回前再次做统一相关性检查。

## POI 质量分类

质量判定使用四种动作，并补全明确语义：

- `reject`：不可访问、停业、施工、非游客区域。
- `downrank`：基座、阶沿石、遗构等细粒度内部构件。
- `allow_with_caution`：存在可疑特征但没有证据表明不可访问，用于测试和可解释评分。
- `allow`：正常候选。

`allow_with_caution` 第一版只影响排序，不对外声称开放状态。硬过滤候选在任何不足场景下都不得重新加入。

## 距离与交通

现有起点距离归一化继续保留。路线总移动距离使用 Haversine 估算的“起点 → 首站 → 相邻站”，页面文案统一使用“约”或“估算”，不把它描述为高德步行路径长度。

交通提示继续按探索范围、估算总距离和水上关键词生成。父级聚合后仍要保留“小瀛洲、岛、洲、湖心、潭塔”等乘船风险判断。

## 错误与降级

- 高德或 DeepSeek 失败时继续使用现有 fallback。
- 候选不足属于可解释降级，不作为服务异常。
- 过滤后没有可行路线时返回现有 `NO_POIS_FOUND`，不改变错误结构。
- refine 或 replace-stop 找不到符合原偏好的新地点时返回现有失败响应，不退回不相关地点。
- 用户取消继续保持立即关闭、不中断选择、不重试、不报红错、不写历史。

## 测试设计

自动化测试中的 DeepSeek 和高德必须全部 Mock，至少新增：

1. 不同 POI ID 但相同父级。
2. 父级 POI 与其子 POI。
3. 同名不同坐标、不同名同 ID、缺失 ID。
4. 全局分配器在候选充足、部分不足、完全不足下的结果和原因。
5. 120 分钟候选充足时达到合理数量；候选不足时不补低质量地点。
6. 博物馆和正餐不会被压缩为不合理的几分钟。
7. 混合偏好下各自定义关键词只约束对应类别。
8. refine 和 replace-stop 继承自定义关键词并剥离内部字段。
9. 用户取消后 HomePage 不写历史记录。
10. 上海、杭州、北京三场景的全链路 Mock 验收。

每个实施阶段执行：

```bash
npm run typecheck
npm test
npm run build
```

## 真实验收

自动化测试通过后，使用线上 DeepSeek 和高德真实运行：

1. 上海外滩：2 小时、1km、吃点东西、面馆、本帮面。
2. 杭州西湖：半天、3km、景点打卡、热门景点、街拍打卡。
3. 北京南锣鼓巷：1 小时、500m、随便逛逛、咖啡茶馆、小众秘境。

逐场记录路线数量、每条地点数、重复 POI、父级重复、距离、预计时间、交通提示、标题和不可访问词。若真实供应不足，允许路线数量或地点数减少，但必须有候选不足解释，且不得放回不可访问或不相关地点。

同时在页面验证：立即取消、15 秒提示、距离未知文案、返回和导航按钮的可访问名称。

## 完成标准

- 所有新增与现有测试通过。
- 类型检查和生产构建通过。
- API 成功响应结构不变，内部字段不泄漏。
- 三个真实场景满足原始验收条件，或在真实候选不足时按设计明确降级。
- 不产生第三方测试额度消耗；只有最终真实验收调用线上服务。
