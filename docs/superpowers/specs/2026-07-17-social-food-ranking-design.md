# 社交平台热门美食榜单设计

## 目标

将纯美食场景保留为“附近美食榜单”，不包装成游玩路线。榜单优先展示在美团、抖音、小红书公开网页搜索结果中有证据的热门门店，同时以高德 POI 作为门店真实性、位置、距离和基础评分的唯一事实来源。

## 成功标准

- 页面展示数量始终等于最终返回的 `stops.length`，不存在“精选 6 家、实际 3 家”。
- 榜单明确标识为美食推荐，而非游玩路线。
- 宴会中心、婚宴厅、单位食堂、会所餐饮、酒店内部餐厅不会进入普通到店推荐。
- 只有存在可追溯的公开搜索结果时，门店才能标记为“平台热门候选”。
- 搜索不可用、额度耗尽或无有效证据时，自动降级为高德评分与距离排序，不影响路线生成主流程。
- 搜索服务使用 Tavily 免费计划，单次榜单生成最多消耗一次基础搜索 credit。

## 数据边界

### 高德 POI

高德负责：

- 门店名称、地址、经纬度和距离；
- POI 类型与基础评分；
- 门店是否位于用户指定范围内；
- 搜索结果与真实门店的身份匹配。

### Tavily 搜索

Tavily 仅负责检索公开网页中的热度证据。查询包含当前位置、商圈和“美团、抖音、小红书、网红美食”等关键词。请求使用基础搜索，每次消耗一个免费 credit。

搜索结果不是门店事实来源。结果标题、摘要或 URL 无法与高德候选门店可靠匹配时，不得用于推荐或加分。

### DeepSeek

DeepSeek 只对已匹配的候选及其搜索证据进行结构化排序和简短总结，不自行联网，不得生成不存在的门店、评分、平台来源或点评。

## 处理流程

1. 高德检索指定范围内的餐饮 POI。
2. 确定性过滤不适合普通用户独立到店消费的地点。
3. 对区域执行一次 Tavily 基础搜索，获取公开平台结果的标题、摘要和链接。
4. 将搜索证据与高德候选按规范化店名匹配；模糊匹配只允许名称存在明确包含关系，不能仅凭地址或品类关联。
5. DeepSeek 在候选集合内排序。有搜索证据的候选优先；高德评分、距离、地方特色和独立到店属性作为次级因素。
6. 最终路线策略执行距离、去重、时间和质量过滤。
7. 在所有过滤结束后重建榜单名称、说明和数量文案。

## 不适合推荐的 POI

以下名称或类型默认排除：

- 宴会中心、宴会厅、婚宴、婚礼会馆；
- 单位食堂、员工餐厅、机关餐厅、学校食堂；
- 私人会所、商务会所中的餐饮；
- 酒店、宾馆内部且不具备独立门店特征的餐厅；
- 仅提供团体接待或场地服务的餐饮设施。

独立品牌餐厅即使位于商业综合体内仍可保留。酒店内餐厅只有在名称、POI 类型和搜索证据都能证明可独立预订到店时才可进入普通榜单；首版采取保守策略，无充分证据即排除。

## 搜索与免费额度控制

- 每次美食榜单生成最多一次 Tavily `basic` 搜索。
- 查询按粗粒度区域生成缓存键，不对每家门店分别搜索。
- 使用 Cloudflare Cache API 缓存成功结果；建议 TTL 为 24 小时。
- Tavily 超时、401、429、5xx 或响应格式异常时立即降级，不重试收费搜索。
- 不缓存密钥、请求头或包含用户精确坐标的原始查询；缓存键使用城市、区县和商圈级文本。
- 预计免费额度支持每月最多 1,000 次未命中缓存的榜单搜索。

## 接口模型

在 `Stop` 增加可选字段：

- `socialEvidence`: 平台证据数组；每项包含 `platform`、`title`、`url`。
- `popularityReason`: 基于证据生成的简短推荐理由。

只有证据匹配成功时返回这些字段。没有证据的降级结果不返回空数组，也不显示平台标签。

路线继续使用现有 `Route` 结构。最终响应前统一生成：

- 有证据：`热门美食精选，共 N 家`；
- 无证据：`附近热门餐厅，共 N 家`。

`N` 必须在最终路线策略过滤后读取实际 `stops.length`。

## 前端展示

- 标题保持“附近美食清单”或调整为“附近热门美食”。
- 副标题不再使用模型早期生成的固定数量，直接根据当前可见地点数计算。
- 有 `socialEvidence` 时展示“平台热门候选”及可打开的来源链接。
- 无证据时只展示高德评分、距离和普通推荐理由。
- 页面增加说明：平台证据来自公开网页搜索，仅供参考；门店信息以高德和商家实际营业情况为准。
- 不使用“游玩路线”“AI 已验证平台热度”等误导性表达。

## 错误处理与降级

搜索服务是可选增强，不得成为生成榜单的单点故障：

- 未配置 `TAVILY_API_KEY`：直接使用高德榜单；
- 免费额度耗尽：记录不含密钥的警告并降级；
- 搜索无结果：正常返回高德榜单；
- DeepSeek 排序失败：使用确定性排序，先有证据，再按高德评分降序、距离升序；
- 最终没有合格餐厅：沿用 `NO_POIS_FOUND` 业务错误。

## 安全与配置

- `TAVILY_API_KEY` 仅配置在 `server/.dev.vars` 和 Cloudflare Pages secret 中，不进入仓库。
- 服务端日志不得输出密钥、Authorization 请求头或完整第三方响应。
- URL 仅允许 `http`/`https`，前端打开外链时使用安全的新窗口属性。

## 测试与验收

### 单元测试

- 非普通到店 POI 过滤规则；
- 平台域名识别和门店名称匹配；
- 有证据、无证据、搜索失败三种排序；
- 最终数量文案与 `stops.length` 一致；
- 内部搜索字段不会污染无证据响应。

### 服务测试

- Tavily 每次生成最多调用一次；
- 401、429、超时和异常 JSON 均可降级；
- DeepSeek 不能添加高德候选集之外的门店；
- 最终策略删减门店后副标题会重新计算。

### 页面验收

- 复现浦东南码头场景，页面显示数量与列表一致；
- 宴会中心不出现；
- 有来源时可看到并打开平台证据；
- 无来源时不显示美团、抖音、小红书推荐声明；
- Tavily 不可用时页面仍能正常展示普通美食榜单。

## 非目标

- 不直接抓取需要登录的平台页面；
- 不绕过美团、抖音或小红书的反爬与访问限制；
- 不承诺搜索引擎能覆盖平台内所有内容；
- 不建立平台热度的长期历史数据库；
- 不将美食榜单改造成多站游玩路线。
