# 两轮用户视角体验 · 2026-09-12

范围：本地 http://localhost:9090/，Computer use，390×844 手机尺寸。使用独立 Codex 预览浏览器的测试计划，未操作用户 Chrome 的真实行程。只体验、只读核对源码与记录意见，未改业务代码，未提交或部署，未写生产数据库。

## 实际走过的流程

1. 重庆：搜索城市 → 自由模式 → 首页滑动入口 → 洪崖洞详情并加入 → 磁器口加入 → 今日计划 → 帮我顺一下 → 导航选项弹层 → 两站模拟到达 → 自动点亮 → 生成票根 → 保存图片生成成功。
2. 南京：首页推荐加入南京博物院、夫子庙 → 开始行程 → 完成南京博物院（1/2）→ 切去重庆查看计划 → 切回南京 → 发现进度归零 → 手动调整顺序 → 重新开始并完成两站 → 足迹页。

结束时独立预览浏览器共有南京、重庆、成都、杭州 4 城足迹。成都、杭州来自此前测试，均保留。重庆生成本轮票根，南京未生成票根也正常点亮。生成的图片提示可长按保存；未验收真实微信相册保存、系统分享或实地 GPS 导航。

## 按影响排序的改进意见

### 1. 高：切换城市后，行程进度丢失

复现：南京 1/2 → 首页切到重庆 → 查看今日计划 → 切回南京。两站地点仍在，但变回“准备好，就开始今天”，南京博物院的已到标记消失。重庆刚完成的行程也变回未开始。

问题：切城提示承诺“今日计划会暂时收起，切回该城市时自动恢复”，用户自然会把打卡进度包含在内。

源码核对：HomePage.applyCitySwitch 无条件 todayJourney.reset()；useTodayJourney 只有一份全局状态，没有按城市保存。此为当前代码中独立于新增足迹历史的旧行为，足迹历史本身未因此消失。

建议：每城保存已到地点、下一站、开始/完成时间；切回恢复完整行程。选择当前同城也不应重置进度。优先于视觉调整。

### 2. 高：误点“到过了”没有单站撤销

实测：点击后立即切到下一站；已到地点只有详情和导航，没有“标错了/撤销”。全程完成后只有“重新开始这趟行程”，无法只纠正某一站。

建议：到达反馈提供短时“撤销”，已到地点保留“改为未到”入口。需同时约定已完成足迹如何修正，避免纠正行程后足迹仍保留错误信息。无需每次打卡都弹确认。

### 3. 中：首次加载会短暂显示错误的空结果

实测：重庆探索进入时显示“0 个符合自由标签”“还没有可推荐的地点”；稍后正常加载出 5 个地点。

源码核对：feedLoading 初始为 false，先读取城市上下文，开始推荐请求后才设为 true。

建议：从进入页面起直到城市上下文和推荐加载结束都显示加载状态；成功返回空数组时才显示空结果，失败单独提供重试。

### 4. 中：停留时长、交通成本和行程强度没有形成明确解释

实测：自由模式选择洪崖洞、磁器口，合计停留 5 小时；今日计划却显示“城市特种兵”。“帮我顺一下”提示当前顺序比较连贯，只给洪崖洞 → 磁器口，没有展示两站间的距离或交通耗时。

源码核对：强度由地点数量、停留时间、最大跨度计算，不是画像切换；但界面缺少解释，容易让用户以为身份被改了。

建议：显示“行程强度：偏满”并说明触发原因；保留自由身份。明确“游玩约 5 小时，交通另计”；有可靠路线数据后再显示交通时间，不能把直线距离包装成实际通勤耗时。首次可先展示两站跨度及需要考虑换乘的提醒。

### 5. 中：首页与探索页的加入前提示不一致

实测：重庆探索中可提前看到“加入后约 5 小时（不含交通）”；南京通过首页详情加入两站时，详情没有同样的合计时长提示，进入计划页才发现预计 7.5 小时。

源码核对：首页 SpotDetailSheet 未传入探索页所用的计划时长提示。

建议：所有加入入口共用加入后的预计停留与负担提示，尤其自由/亲子模式。地点详情还应提供可核对的官方开放/预约入口；本轮仅看到通用提醒，未核查场馆当日开放信息。

- 探索的跳过、详情、加入三个动作清楚，加入后可继续下一张。
- 手动调整顺序立即生效。
- 完成行程自动点亮，票根生成独立，旧足迹仍保留。
- 票根图片生成成功，保存说明没有虚称已存入系统相册。
